# AI-संचालित प्रोजेक्ट मैनेजमेंट सिस्टम – Requirement Document

12 अक्टूबर 2026 · Sohil

## 1. विज़न और उद्देश्य

लक्ष्य: एक नॉन-टेक्निकल मालिक, Claude की मदद से, सारे प्रोजेक्ट का सपोर्ट, मेंटेनेंस और नया डेवलपमेंट खुद संभाल सके — पूरी टीम न हो तब भी कंपनी का काम न अटके।

- **डिपेंडेंसी खत्म:** कोड, जानकारी और कंट्रोल किसी डेवलपर के दिमाग़ में नहीं, कंपनी के सिस्टम में रहे।
- **कहीं से भी, कभी भी:** मोबाइल या कंप्यूटर से, दिन हो या रात, क्लाइंट का चेंज या एरर संभाला जा सके।
- **लाइव पर असर नहीं:** हर बदलाव पहले beta में बने और टेस्ट हो, लाइव डेटाबेस और यूज़र सुरक्षित रहें।
- **कम से कम ख़र्च:** भारी काम Claude सब्सक्रिप्शन पर, सिर्फ़ ज़रूरी ऑटोमेशन API पर।
- **टीम का आकार:** पहले 12 से 5 डेवलपर, 3-4 महीने के टेस्ट के बाद शून्य फ़ुल-टाइम डेवलपर तक जाने का रास्ता।
- **तकनीक से स्वतंत्र:** Laravel, Python/Flask, Flutter या कोई भी स्टैक — सिस्टम हर पर एक जैसा चले।

## 2. वर्तमान स्थिति और समस्या

आज छोटा चेंज डेवलपर से 3-4 दिन लेता है, जबकि मालिक वही काम Claude से आधे से एक दिन में कर लेता है।

| पहलू | आज की हालत |
| --- | --- |
| टीम | 10-12 डेवलपर, ख़र्च ज़्यादा, काम कम |
| प्रोजेक्ट | लगभग 50, जिनमें 5-10 में रोज़ चेंज आते हैं |
| टेक्नोलॉजी | ज़्यादातर Laravel (backend + admin) और Flutter (मोबाइल ऐप); कुछ Python/Flask |
| कोड कहाँ | अलग-अलग लोगों के अलग GitHub अकाउंट |
| होस्टिंग | क्लाइंट का cPanel या कंपनी का Linux VPS |
| Flutter release | डेवलपर 4-5 दिन के चेंज जोड़कर एक साथ स्टोर पर डालता है |
| सबसे बड़ा जोखिम | टीम मना करे या छोड़ दे तो काम रुक जाता है |

## 3. सिस्टम की नींव

हर प्रोजेक्ट चार चीज़ों पर टिकेगा; ये तैयार हुए बिना बाक़ी ऑटोमेशन भरोसेमंद नहीं होगा।

1. **कंपनी का एक GitHub अकाउंट** — सारे 50 प्रोजेक्ट यहीं, मालिक के कब्ज़े में। हर बदलाव की पूरी history, यही कोड का बैकअप भी है।
2. **हर प्रोजेक्ट के तीन environment** — local (काम करने की जगह), beta (टेस्ट और क्लाइंट review), live (असली यूज़र)। beta और live की बनावट एक जैसी हो।
3. **Automated tests** — हर चेंज के बाद अपने-आप चलें, ताकि Claude का चेंज कुछ और न तोड़े।
4. **एक-बटन deploy और instant rollback** — गड़बड़ हो तो पिछली हालत में तुरंत वापसी।

**प्रोजेक्ट नॉलेज फ़ाइल:** हर रिपॉज़िटरी में एक फ़ाइल हो जो बताए — प्रोजेक्ट क्या करता है, कैसे चलता है, कहाँ deploy होता है, कौन-से environment variables लगते हैं। यही Claude का context है, और यही डेवलपर-डिपेंडेंसी तोड़ने की चाबी है।

**होस्टिंग:** VPS पर पूरा pipeline आसानी से बनेगा। cPanel वाले प्रोजेक्ट में deploy सीमित रहता है; जहाँ संभव हो उन्हें धीरे-धीरे VPS पर लाना बेहतर है।

## 4. रोज़ के चेंज का फ़्लो

क्लाइंट का चेंज कभी सीधे live नहीं जाता: Claude beta में बदलता है, टेस्ट पास होते हैं, क्लाइंट खुद beta में देखकर approve करता है, तब मालिक एक बटन से live करता है।

```
क्लाइंट का चेंज (स्क्रीनशॉट / वीडियो / ऑडियो)
        ↓
डैशबोर्ड चैटबॉट  →  Live से Beta sync (ताज़ा डेटा)
        ↓
Claude beta में बदलाव करे  →  automated tests चलें
        ↓
टेस्ट पास?
   ├─ नहीं → Claude फिर फ़िक्स करे (ऊपर वापस)
   └─ हाँ
        ↓
क्लाइंट को beta लिंक (WhatsApp या ईमेल)
        ↓
क्लाइंट Approve?
   ├─ नहीं → बदलाव फिर से (Claude के पास वापस)
   └─ हाँ
        ↓
Snapshot + Go Live (मालिक का एक बटन, OTP पुष्टि)
        ↓
Live + मॉनिटरिंग (अलर्ट मोबाइल पर)
        ↓
error आए? → Rollback + debug → फिर beta से वही फ़्लो
```

टेस्ट फ़ेल हो या क्लाइंट मना करे तो काम वापस Claude के पास जाता है; live में error आए तो पहले rollback, फिर वही फ़्लो beta से। क्लाइंट का approval रिकॉर्ड रहता है, ताकि बाद में "ये नहीं माँगा था" वाला विवाद न हो। क्लाइंट के लिए beta लिंक के साथ एक छोटा "क्या-क्या जाँचना है" नोट जाए।

## 5. Beta बनाम Live डेटा

Beta और live के डेटाबेस अलग रहेंगे, पर टेस्ट से पहले beta में live की ताज़ा कॉपी आएगी — ताकि live का bug beta में भी दिखे।

- **ताज़ा कॉपी का बटन:** "Live से Beta sync" — live डेटाबेस की उसी पल की कॉपी beta में। असली डेटा जस-का-तस रहेगा (नंबर, लाइसेंस प्लेट वगैरह), ताकि क्लाइंट की शिकायत असली रिकॉर्ड पर वेरिफ़ाई हो सके।
- **बाहर जाने वाले मैसेज का स्विच:** beta में SMS, WhatsApp, ईमेल, पुश नोटिफ़िकेशन default रूप से बंद।
- **टेस्ट-नंबर मोड:** एक तीसरा मोड जिसमें सारे मैसेज सिर्फ़ तय टेस्ट नंबर/ईमेल पर जाएँ, असली यूज़र को कभी नहीं। क्लाइंट या मालिक पूरा फ़्लो खुद देख सके।
- **पेमेंट टेस्ट मोड:** beta में पेमेंट गेटवे हमेशा sandbox/test keys पर, असली पैसा कभी न कटे।

**Busy प्रोजेक्ट (रोज़ 100-500 एंट्री):** beta में टेस्ट के दौरान live में नया डेटा आता रहेगा। इसलिए:

- डेटाबेस का हर बदलाव (migration) ऐसा लिखा जाए कि live के ताज़ा डेटा पर भी सुरक्षित चले — पुराना डेटा मिटे या टूटे नहीं।
- live पर डालने से ठीक पहले एक snapshot अपने-आप बने।
- live करने से पहले एक आख़िरी ताज़ा sync और तेज़ दोबारा टेस्ट।

## 6. मोबाइल डैशबोर्ड (Admin Panel)

एक ही डैशबोर्ड, मोबाइल और कंप्यूटर दोनों पर, जहाँ से सारे प्रोजेक्ट दिखें और चलें — मालिक खुद Claude के साथ बनाएगा, किसी डेवलपर से नहीं।

**मुख्य स्क्रीन**

- सारे प्रोजेक्ट की लिस्ट, हर एक के आगे स्टेटस: हरा (ठीक), पीला (ध्यान दें), लाल (एरर/डाउन)।
- हर प्रोजेक्ट पर: आख़िरी deploy, आख़िरी बैकअप, खुले चेंज रिक्वेस्ट, क्लाइंट approval बाक़ी।

**प्रोजेक्ट के अंदर**

- **प्रोजेक्ट चैटबॉट:** चेंज लिखें या स्क्रीनशॉट, वीडियो, ऑडियो डालें; Claude (API से) काम करे।
- **बटन:** Live से Beta sync · Beta में deploy · क्लाइंट को beta लिंक भेजें · Go Live · Rollback · अभी बैकअप लें · Restore · मैसेज स्विच (बंद / टेस्ट-नंबर / चालू)।
- **Debug live error:** live का error log पढ़कर Claude beta में फ़िक्स करे, फिर सामान्य फ़्लो।
- **Project Clone / Description डाउनलोड** (सेक्शन 11)।
- **Flutter release बटन** (सेक्शन 12)।

**सूचनाएँ:** साइट डाउन, error, बैकअप फ़ेल, क्लाइंट approval — सब मोबाइल पर तुरंत।

## 7. बैकअप और रिस्टोर

कोड का बैकअप GitHub में अपने-आप है; असली जोखिम डेटाबेस और अपलोड की गई फ़ाइलों का है, उनका बैकअप अपने-आप और सर्वर से बाहर रहेगा।

| क्या | कब | कहाँ |
| --- | --- | --- |
| कोड | हर बदलाव पर | कंपनी GitHub |
| डेटाबेस | रोज़ एक बार, अपने-आप | सर्वर से बाहर cloud storage |
| डेटाबेस snapshot | हर Go Live से ठीक पहले | cloud storage |
| अपलोड फ़ाइलें (इमेज, डॉक्यूमेंट) | रोज़ | cloud storage |

- डैशबोर्ड पर हर प्रोजेक्ट का "आख़िरी बैकअप कब" दिखे; पुराना पड़े तो लाल।
- **Restore बटन:** किसी भी तारीख़ के बैकअप से beta या live वापस लाना।
- **महीने में एक बार restore की जाँच:** बैकअप सच में चलता है या नहीं, beta पर restore करके देखना।

## 8. सिक्योरिटी, मॉनिटरिंग और रिकवरी

साइट हैक या डाउन हो तो मैन्युअल बैकअप ढूँढने की जगह एक बटन से आख़िरी साफ़ version मिनटों में वापस आएगा।

**पहले से बचाव**

- हर प्रोजेक्ट के आगे WAF / firewall (जैसे Cloudflare) जो आम हमले रोके।
- Uptime और बदलाव मॉनिटर: हर कुछ मिनट में साइट और होम पेज जाँचे; डाउन हो या पेज बदले तो क्लाइंट के फ़ोन से पहले मालिक को अलर्ट।
- सर्वर और फ़्रेमवर्क अपडेट, मज़बूत पासवर्ड, SSH key।

**हमला या डाउन होने पर**

1. अलर्ट मोबाइल पर आए।
2. **Restore last good version:** GitHub से आख़िरी साफ़ कोड दोबारा deploy, ज़रूरत हो तो डेटाबेस snapshot से।
3. Claude से live logs जँचवाएँ — कहाँ से घुसा, क्या बदला।
4. beta में छेद बंद करें, टेस्ट करें, फिर live।

गहरे हमले (डेटा चोरी, सर्वर में घुसपैठ) दुर्लभ हैं, पर इनके लिए एक भरोसेमंद on-call एक्सपर्ट का संपर्क रखना समझदारी है।

## 9. यूज़र एक्सेस, अधिकार और लॉग

पूरा कंट्रोल मालिक के पास; हर डेवलपर को सिर्फ़ वही प्रोजेक्ट और वही बटन दिखें जो उसे दिए गए हैं।

| भूमिका | क्या देख सकता है | क्या कर सकता है |
| --- | --- | --- |
| Owner (मालिक) | सारे प्रोजेक्ट | सब कुछ, Go Live, यूज़र जोड़ना-हटाना |
| Developer | सिर्फ़ असाइन किए प्रोजेक्ट | beta में चेंज और टेस्ट; Go Live तभी जब मालिक दे |
| Client | अपना beta लिंक | देखना, टिप्पणी, Approve / Reject |

- हर इंसान का अपना लॉगिन; कोई आईडी-पासवर्ड शेयर नहीं।
- हर लॉगिन पर OTP (two-factor)।
- **Activity log:** किसने, कब, किस प्रोजेक्ट में, कौन-सा प्रॉम्प्ट और क्या बदला — सब दर्ज।
- कोई टीम छोड़े तो एक बटन से उसी पल सारा एक्सेस बंद।
- Go Live और Restore जैसे बड़े काम पर मालिक को अलग से पुष्टि (OTP)।

## 10. Claude इस्तेमाल का मॉडल और ख़र्च

भारी, एक बार का काम सब्सक्रिप्शन पर Claude Code में; रोज़ का हल्का, अपने-आप चलने वाला काम डैशबोर्ड से API पर — दोनों GitHub से जुड़े।

| काम | कहाँ | ख़र्च |
| --- | --- | --- |
| नया प्रोजेक्ट या बड़ा मॉड्यूल बनाना | Claude Code (मालिक का अपना लॉगिन) | सब्सक्रिप्शन |
| रोज़ के छोटे चेंज, debug, फ़िक्स | डैशबोर्ड का प्रोजेक्ट चैटबॉट | API, इस्तेमाल के हिसाब से |
| डेवलपर का काम (अगर कोई हो) | उसका अपना सब्सक्रिप्शन / VS Code extension | उसका अपना प्लान |

**ज़रूरी नियम**

- सब्सक्रिप्शन (Pro/Max) सिर्फ़ इंसान के सीधे इस्तेमाल के लिए है। उसे अपने डैशबोर्ड के पीछे जोड़ना या iframe में डालकर अपने-आप चलवाना संभव और मान्य नहीं है; डैशबोर्ड के लिए API ही रास्ता है।
- मालिक का लॉगिन किसी से शेयर नहीं — इससे अकाउंट बंद होने का ख़तरा है।

**GitHub sync:** कंपनी GitHub ही "सच का स्रोत" है। Claude Code में बना नया प्रोजेक्ट GitHub में जाते ही डैशबोर्ड उसे अपने-आप सूची में दिखाए; डैशबोर्ड से जोड़ा प्रोजेक्ट भी GitHub में बने — दोनों तरफ़ एक जैसी लिस्ट।

**अंदाज़न API ख़र्च:** छोटे रोज़ के चेंज वाले हर active प्रोजेक्ट पर महीने के लगभग $50-150 (करीब ₹4,000-12,000)। यह मोटा अनुमान है; पहले 1-2 प्रोजेक्ट पर एक महीना चलाकर असली बिल देखें।

**सब्सक्रिप्शन:** शुरुआत छोटे प्लान से; रोज़ की लिमिट कम पड़े तो Max पर जाएँ।

## 11. नया प्रोजेक्ट, Project Clone और SaaS

चालू प्रोजेक्ट को कभी सीधे नहीं छेड़ा जाएगा; बड़ा बदलाव हमेशा एक नए, अलग प्रोजेक्ट में होगा और तैयार होने पर ही live जाएगा।

**नया प्रोजेक्ट जोड़ना**

1. डैशबोर्ड पर "नया प्रोजेक्ट": नाम, requirement (.md फ़ाइल), डोमेन, सर्वर, डेटाबेस की डिटेल भरें।
2. सिस्टम GitHub रिपॉज़िटरी, beta और live environment, ब्रांच अपने-आप बनाए।
3. डोमेन/DNS पॉइंट करना और SSL स्क्रिप्ट — मालिक खुद या एक बटन से।
4. असली कोड Claude Code में (सब्सक्रिप्शन पर) बने, GitHub में जाए, और beta पर अपने-आप चले।

**Project Clone / Description**

- किसी भी प्रोजेक्ट पर "Project Description बनाओ" बटन: Claude कोड, डेटाबेस टेबल स्ट्रक्चर और फ़्लो पढ़कर एक पूरा requirement document बनाए।
- डाउनलोड OTP या पासवर्ड से सुरक्षित, और activity log में दर्ज।
- **Clone:** उसी description से नया प्रोजेक्ट; पुराना अछूता।

**Clone के दो इस्तेमाल**

| इस्तेमाल | क्या बदलेगा |
| --- | --- |
| वही प्रोजेक्ट दूसरे क्लाइंट को बेचना | सिर्फ़ लोगो, नाम, नंबर, रंग, डोमेन |
| SaaS में बदलना (जैसे ABC → ABC SaaS) | कई क्लाइंट एक सिस्टम में, हर एक का डेटा अलग |

**चालू प्रोजेक्ट में नया मॉड्यूल:** beta में बने, क्लाइंट approve करे, फिर live डेटाबेस में बिना पुराना डेटा छेड़े जुड़े।

**SaaS पर सावधानी:** हर क्लाइंट का डेटा अलग रखने का design और पुराने डेटा का नए ढाँचे में merge सबसे नाज़ुक कदम हैं — live करते समय एक अनुभवी नज़र साथ रखें।

## 12. Flutter मोबाइल ऐप release

Backend और API के चेंज रोज़ live हो सकते हैं, पर ऐप के चेंज हफ़्ते में एक बार एक साथ जाएँगे, क्योंकि स्टोर review में 1-2 दिन लगते हैं और वह किसी के कंट्रोल में नहीं।

- ऐप के चेंज जमा होते रहें; डैशबोर्ड पर "Release तैयार" सूची दिखे।
- **Build & Submit बटन:** ऐप build होकर Play Store और App Store पर अपने-आप सबमिट (Play Console और App Store Connect की access एक बार सेट)।
- पहले internal / TestFlight टेस्ट ट्रैक पर, फिर production।
- **Backward compatibility:** API बदले तो पुराना ऐप जो यूज़र के फ़ोन में है, वो न टूटे — API के पुराने रूप तब तक चलते रहें जब तक ज़्यादातर यूज़र अपडेट न कर लें।
- ज़रूरी हो तो ऐप में "force update" संदेश।

## 13. क्या संभव है: ईमानदार आकलन

यह विज़न लगभग 90-95% हासिल किया जा सकता है; सर्वर कंपनी या स्टोर review जैसी बाहरी दिक़्क़तें इस गिनती से बाहर हैं।

| हिस्सा | संभावना |
| --- | --- |
| मोबाइल डैशबोर्ड, beta-live फ़्लो, क्लाइंट approval | पक्का |
| बैकअप, restore, साइट वापस चालू करना | पक्का |
| एक्सेस कंट्रोल, लॉग, OTP | पक्का |
| रोज़ के चेंज और debug सिर्फ़ प्रॉम्प्ट से (चाहे 20-30 प्रॉम्प्ट लगें) | ज़्यादातर बार |
| Flutter build और स्टोर सबमिट बटन | पक्का (approval स्टोर के हाथ में) |

**बचा हुआ गैप (5-10%)**

- कभी-कभार कोई पेचीदा गुत्थी जहाँ नॉन-टेक्निकल होकर Claude को सही दिशा देना मुश्किल हो। शुरुआती महीनों में यह ज़्यादा, समय के साथ महीने में एक बार या कम।
- SaaS जैसे बड़े architecture बदलाव और गहरे सिक्योरिटी हादसे — यहाँ on-call एक्सपर्ट का संपर्क रखें।

**समय:** एक प्रोजेक्ट पर पहला चलता version 2-3 महीने; सारे प्रोजेक्ट पर 3-6 महीने।
