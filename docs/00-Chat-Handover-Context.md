## 1. मैं कौन हूँ और कैसे बात करता हूँ

- नाम: सोहिल। एक IT कंपनी का मालिक, **नॉन-टेक्निकल**।
- भाषा: **हिंदी**। ज़्यादातर voice से बोलकर लिखता हूँ, इसलिए स्पेलिंग/शब्द गड़बड़ हो सकते हैं — मतलब समझकर जवाब दो।
- सीधा, साफ़ और ईमानदार जवाब चाहिए; टेक्निकल शब्द हों तो सादी भाषा में समझाओ।
- मैं पहले ख़ुद Claude से एक accounting software बना चुका हूँ।
- बातचीत का नाम पहले "Product launch" रखा था — वह सिर्फ़ नाम था। **असली और इकलौता प्रोजेक्ट यही AI डैशबोर्ड है।**

## 2. आज की स्थिति (समस्या)

- 10-12 डेवलपर; ख़र्च ज़्यादा, काम कम; उन पर पूरी निर्भरता।
- लगभग 50 क्लाइंट प्रोजेक्ट; रोज़ के चेंज सिर्फ़ 5-10 प्रोजेक्ट में आते हैं।
- टेक स्टैक: ज़्यादातर **Laravel** (backend + admin panel) + **Flutter** (मोबाइल ऐप); कुछ Python/Flask।
- कोड अलग-अलग डेवलपर्स के निजी GitHub अकाउंट में बिखरा है; कंपनी का GitHub organization बनाना है।
- होस्टिंग: क्लाइंट का cPanel या कंपनी का Linux VPS।
- छोटा चेंज डेवलपर से 3-4 दिन लेता है; मैं ख़ुद Claude से वही आधे-एक दिन में कर लेता हूँ।
- Flutter डेवलपर 4-5 दिन के चेंज इकट्ठा करके स्टोर पर डालता है।

## 3. विज़न

- **"Zero developer"** का मतलब: पूरी टीम चली जाए तब भी काम न अटके; कोई भी मुझ पर hold न रख सके।
- मोबाइल या कंप्यूटर से, दिन-रात कभी भी, क्लाइंट का चेंज (स्क्रीनशॉट / वीडियो / ऑडियो) डैशबोर्ड में डालूँ और प्रॉम्प्ट से हल हो।
- 20-30 प्रॉम्प्ट लगें तो चलेगा, पर इंसानी डेवलपर की ज़रूरत **महीने में एक बार से ज़्यादा न पड़े**।
- सर्वर डाउन जैसे बाहरी कारण विज़न से बाहर हैं।
- **सबसे बड़ी प्राथमिकता: कम से कम ख़र्च।**

## 4. पक्के हो चुके फ़ैसले

### नींव
- कंपनी का **एक GitHub organization**; सारे प्रोजेक्ट उसमें। GitHub = "सच का स्रोत", दोनों तरफ़ auto-sync।
- हर प्रोजेक्ट के तीन environment: **local / beta / live**।
- automated tests; एक-बटन deploy; instant rollback।
- हर रिपॉज़िटरी में **प्रोजेक्ट नॉलेज फ़ाइल** — यही डेवलपर डिपेंडेंसी तोड़ने की चाबी है।

### रोज़ के चेंज का फ़्लो
क्लाइंट का चेंज → डैशबोर्ड चैटबॉट → Live से Beta sync → Claude beta में बदले → tests → क्लाइंट को beta लिंक (WhatsApp/ईमेल) → क्लाइंट Approve → Snapshot + Go Live (सिर्फ़ मेरा बटन, OTP से) → मॉनिटरिंग → error हो तो rollback + debug।
- क्लाइंट approval का रिकॉर्ड रहे, ताकि बाद में विवाद न हो।

### Beta बनाम Live डेटा
- beta और live के DB अलग, पर हर टेस्ट से पहले live की ताज़ा कॉपी beta में।
- **डेटा masking नहीं करनी** — मेरा पार्किंग-साइट उदाहरण: लाइसेंस प्लेट / मोबाइल नंबर से verification होता है, नकली डेटा से टेस्ट बेकार।
- इसकी जगह: beta में बाहर जाने वाले मैसेज का **on/off स्विच + "टेस्ट-नंबर मोड"**, और **payment sandbox**। (यह मेरा अपना सुझाव था; Claude ने masking का सुझाव वापस लिया।)
- Busy प्रोजेक्ट (रोज़ 100-500 एंट्री): migration live के ताज़ा डेटा पर टेस्ट; Go Live से पहले snapshot; live से ठीक पहले आख़िरी sync + दोबारा टेस्ट।

### बैकअप
- कोड GitHub में; DB रोज़ ऑटो + हर Go Live से पहले snapshot; अपलोड फ़ाइलें रोज़।
- सब कुछ सर्वर से बाहर cloud storage में (सुझाव: Cloudflare R2 या Backblaze B2)।
- डैशबोर्ड पर "आख़िरी बैकअप कब"; महीने में एक बार restore की असली जाँच।

### सिक्योरिटी
- WAF/Cloudflare, uptime + page-change monitor, "Restore last good version" बटन।
- गहरे हमलों के लिए एक on-call एक्सपर्ट।
- मैंने पूछा था: जब Claude बेहतर काम करता है तो डेवलपर क्यों? जवाब: फ़र्क क्षमता का नहीं, **ज़िम्मेदारी, फ़ैसले और verification** का है — इसलिए सिर्फ़ on-call एक्सपर्ट, फ़ुल-टाइम टीम नहीं।

### एक्सेस
- Role-based: **Owner / Developer / Client**। हर इंसान का अपना लॉगिन, कोई शेयरिंग नहीं।
- OTP/2FA; पूरा activity log; एक बटन से किसी का एक्सेस बंद; Go Live / Restore पर अलग OTP।

### Claude का ख़र्च मॉडल (सबसे ज़्यादा चर्चा वाला मुद्दा)
- मैं चाहता था कि Claude subscription को डैशबोर्ड के पीछे या iframe में जोड़कर API का ख़र्च बचाऊँ। **Claude ने साफ़ मना किया** — यह नियमों के ख़िलाफ़ है और तकनीकी रूप से भी संभव नहीं। डैशबोर्ड सिर्फ़ **Claude API key** से चलेगा।
- **अंतिम सहमति:**
  - भारी / एक-बार का काम (नया प्रोजेक्ट, बड़ा मॉड्यूल) → **Claude Code में subscription पर**।
  - रोज़ का छोटा ऑटोमेशन → **डैशबोर्ड से API पर**।
  - डेवलपर अपने-अपने subscription रखें; मेरा लॉगिन किसी को नहीं।
- API ख़र्च का अनुमान: हर active प्रोजेक्ट पर महीने के लगभग **$50-150 (₹4,000-12,000)**। पहले 1-2 प्रोजेक्ट पर एक महीना चलाकर असली बिल देखना है।

### नया प्रोजेक्ट
- डैशबोर्ड के फ़ॉर्म से → repo, environments, branches अपने-आप बनें।
- असली कोड Claude Code में subscription पर लिखा जाए (API बचत)।
- DNS/SSL मैं ख़ुद कर सकता हूँ — इसे कमी नहीं माना।

### Project Clone (नाम पहले "SaaS clone" था, मैंने "Project Clone" करवाया)
- किसी भी प्रोजेक्ट का अपने-आप requirement / description बने (कोड + DB टेबल स्ट्रक्चर + फ़्लो से)।
- डाउनलोड OTP/पासवर्ड से सुरक्षित, activity log में दर्ज।
- दो इस्तेमाल: (1) वही प्रोजेक्ट दूसरे क्लाइंट को बेचना (लोगो / नाम / नंबर / डोमेन बदलकर), (2) उसे SaaS में बदलना।

### SaaS conversion (ABC → ABC SaaS)
- पुराना प्रोजेक्ट बिल्कुल नहीं छुआ जाएगा; SaaS एक अलग नया प्रोजेक्ट होगा।
- सबसे नाज़ुक हिस्से: multi-tenant (हर ग्राहक का डेटा अलग) design और पुराने डेटा का merge। Live करते समय किसी अनुभवी की नज़र ज़रूरी।

### Flutter ऐप
- backend/API रोज़ live हो सकता है; ऐप हफ़्ते में एक बार बैच release।
- डैशबोर्ड पर Build & Submit बटन (Play Console + App Store Connect); पहले internal testing / TestFlight।
- API में backward compatibility (पुराना ऐप न टूटे); ज़रूरत हो तो force-update संदेश।
